# Product facts

What is actually true about MySaveFile, written so it can be handed to a person
or an LLM without either of them having to guess.

This replaces the old root-level `PRODUCT_FACTS.md`, which was gitignored, never
committed, and therefore invisible to every change that made it wrong.

## Structure

```
docs/product-facts/
  README.md              ← you are here: the rules
  do-not-claim.md        ← what we must never say. Read before writing anything public.
  glossary.md            ← the game's words, our words, and the pairs that get mixed up
  surfaces/*.md          ← one file per screen, all the same shape
  PRODUCT_FACTS.md       ← generated by `npm run product-facts`. Gitignored; never hand-edited.
```

One file per surface so a product change touches one small file, not a monolith.
`npm run product-facts` concatenates the lot into a single
`docs/product-facts/PRODUCT_FACTS.md` for pasting into a Claude project — the
rules and the two constraint files first, then every surface.

There is no `00-core-model.md`. It was planned and dropped: `surfaces/re-sync.md`
already explains mirrored-versus-authored, what survives and what yields, in more
depth than a summary of it would.

## The rules

**0 · Read the files whole. Never grep.** This is the rule the others depend on.
A search returns only what you already thought to look for, so it can confirm a
guess but never correct one. Two versions of the households page were written
from searches and both invented mechanics the code flatly contradicted — each
time by a line a few rows from what was already open. Reading whole also surfaces
what nobody thought to ask: the 8-sim cap, tree-only survivors of a deleted
household, lifestage being locked on save-backed sims.

Behaviour lives in **three layers**, and all three get read:

| Layer | Answers | Where |
|---|---|---|
| The screen | what you see and click | the components |
| The store | what actually persists | `useSaveFile.ts`, the API routes |
| The sync | what a re-sync does to it | `diff.ts`, `snapshot.ts`, `plannedMoveSync.ts` |

Reading only the first is how both wrong versions happened. Budget a few thousand
lines per surface and one long sitting — it is much cheaper than unwinding a
page that read plausibly and wasn't true.

**1 · Nothing goes in from memory.** Every claim comes from code, from the
running app, or from the user. If it can't be traced it doesn't go in.

**2 · Anything countable is generated, never written.** Route lists, world
lists, lot types, pack gating, parsed fields. That's the class of fact that goes
subtly wrong when written by hand, and a script gets it right every time.

**3 · Every surface file carries a `Verified` line** — how, and when. If you
can't say how you checked, you haven't checked.

**4 · Uncertainty is stated, not smoothed over.** A `Needs confirming` section
is a normal part of a surface file, not a failure. A confident sentence that
turns out to be wrong costs far more than an open question.

**5 · Existence is not readiness.** Each surface carries a polish rating, because
a feature can work perfectly and still not be ready to photograph.

**6 · Present tense. No history, ever.** A surface file says what the product
does. It never says what it used to do, when that changed, or that something was
fixed — no "FIXED", no "used to", no "no longer", no dated decisions, no
changelog sections. This is not a style preference: a file that narrates its own
edits stops being readable as fact, and anyone writing from it has to work out
which half is current.

The rule to apply when you're tempted: **is what's left a fact about the product,
or only a note about a change?** A reason belongs in ("the snapshot is written
once, because units would otherwise overwrite each other"). A before-and-after
does not ("it used to be written per record"). Change history lives in git and in
the running-order artifact, and open work lives in the running order too — never
here. The only date a surface file carries is on its `Verified` line.

## Tiers

Tier controls the **verification bar**, not how much is written. Every surface
gets the same full treatment.

| Tier | Bar |
|---|---|
| **1** | Every claim driven in the running app and screenshotted before it is written down. |
| **2** | Checked against code, and its relationship to sync spelled out explicitly. |
| **Output** | Written *from* this sheet, not described by it. See below. |
| **Exclude** | Internal tools. Not product surfaces, and not described at all. |

### Output surfaces: landing, help, about

These three are prose *about* the product. They have no mechanics of their own —
everything they say is something a surface file already says, so a fact file
describing them would be documenting a description, and the two would drift the
moment either changed.

They run the other way: **they get written from the finished sheet**, and then
**checked back against it** before go-live. That review is the highest-value one
in the whole exercise, because a wrong claim here is a wrong claim in public.

### Don't document a surface that's mid-redesign

`/saves`, the first-run screen and save settings are being reworked (mockups:
the sync & save-management artifact). Documenting them now buys a file that's
wrong on the day the redesign lands. Do the redesign, then describe what it
became. The same test applies to anything else with an open design pass.

## The surface template

Every file in `surfaces/` has these headings, in this order, so an LLM can
traverse them mechanically:

```
# <Name>
Route · Tier · Requires · Polish · Verified

## Why it exists          — the job it does for a player, in one paragraph
## What you see           — the layout, so it can be described without a screenshot
## What you can do        — capabilities, GROUPED BY WHAT YOU'RE ACTING ON
## What you can't         — capability limits. Feeds do-not-claim.
## How it relates to sync — what mirrors the save, what you authored, what a
                            re-sync does to it. Never omitted, on any surface.
## Limitations            — where what it does do is thinner than it looks
## Needs confirming       — open questions, one or two lines each. OMIT the
                            heading entirely when nothing is open; a section
                            over the word "none" is noise.
```

**The last three are different questions**: *What you can't* is what the product
won't let you do, *Limitations* is where what it does do falls short, and *Needs
confirming* is what nobody has decided yet. Keep the last one to actual
questions — once a bullet turns into an explanation it isn't open any more, and
belongs in Limitations.

### One screen often edits more than one thing

**Group "What you can do" by object, and name each group.** The first draft of
`households.md` listed only household verbs — create, rename, assign, delete —
and missed that the whole third column is a per-sim editor with six cards in it.
Roughly a third of the screen went undescribed, because the list was written
from the page's *name* rather than from the page.

Use the same discipline everywhere: walk the screen, not the noun in its title.

### Use the app's own words

If a label exists in the build, quote it exactly — **Rest of Town**, **From
save**, **Died of**, **Moving out**. Don't paraphrase and don't invent a
synonym. These have been through review; the build is the authority, not a
plausible-sounding alternative.

## Keeping it true

Changing a user-facing surface means updating its file **in the same commit**.
That rule is in the repo's `CLAUDE.md`, and it is enforced rather than trusted.

**The `Verified` line is the machinery.** It already names the source files a
surface was written from, so it doubles as the map from code to documentation —
one that can't drift from the doc, because it *is* the doc. Two things read it:

| Command | Answers |
|---|---|
| `npm run facts:check` | Which surface files are behind the code they describe, and which files moved after the doc did |
| the `commit-msg` hook | Does *this commit* change something a surface file describes, without touching that file |

The hook **refuses the commit** and names the file to update. Deliberate skips
put `[no-facts]` in the commit message — a refactor, a test, a build change,
anything a user could not notice. Files named by more than three surfaces are
treated as shared spine (`GameReimport.tsx`, `useSaveFile.ts`, `api.ts`): they
print a note and never block, because demanding twelve doc updates for one edit
to the sync spine would turn the check into noise, and noise gets bypassed.

Hooks are per-clone, so a fresh checkout needs `git config core.hooksPath
.githooks` once. The hook itself lives in `.githooks/commit-msg`, tracked, so
there's nothing to reconstruct.

This is the replacement for what failed last time: the old fact sheet was
gitignored, so no change ever put it in a diff and nobody could have noticed it
rotting.
